# Contributing

## Pull requests

Use a focused pull request with a Conventional Commit-compatible title:

```text
<type>(<optional scope>)!: <description>
```

The scope is optional. Write a concise English description starting with a lowercase character.

| Type | Use | Release effect |
| --- | --- | --- |
| `feat` | User-visible functionality | Minor |
| `fix` | Bug fix | Patch |
| `deps` | Dependency update | Patch when recognized by Release Please |
| `docs` | Documentation only | None by default |
| `refactor` | Restructuring without behavior change | None by default |
| `test` | Tests only | None by default |
| `chore` | Repository maintenance | None by default |
| `ci` | Continuous integration | None by default |
| `build` | Build configuration | None by default |
| `revert` | Revert an earlier change | Determined from the reverted change |

Examples:

```text
feat: select the previous active sheet by default
fix(search): ignore stale sheet entries
docs: document the release process
chore(deps): update a GitHub Action
feat!: change the extension storage format
```

Use `!` after the type or scope, or a `BREAKING CHANGE:` footer, for a breaking change.

Pull requests are squash merged. The pull request title becomes the commit subject on `main`, so it determines the version and changelog entry generated by Release Please.

## Verification

```bash
npm test
```

## Releases

Release Please opens a release pull request after releasable changes reach `main`. It updates `package.json`, `manifest.json`, `.release-please-manifest.json`, and `CHANGELOG.md` together.

Review and merge that pull request to create the `v<version>` Git tag and GitHub Release. This repository does not publish an npm package automatically.

Workflows from external forks remain pending until a maintainer explicitly approves them. Fork workflows receive no repository secrets or write token.
